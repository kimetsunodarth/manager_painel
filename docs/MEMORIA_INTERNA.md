### Contexto

O usuário queria uma forma de monitorar e atuar nas VMs geridas por duas fontes externas ao Ananim:

1. **Cloud8** (`app.cloud8.com.br`) — plataforma de FinOps/gestão multicloud (não é provedor de nuvem; conecta via AK/SK do próprio cliente nas contas Huawei/AWS/Azure/Oracle). Sem API pública (confirmado: "Integrações" no Cloud8 é só webhook de notificação de eventos, não API self-service).
2. **Huawei COC** (Cloud Operations Center) — Scheduled O&M nativo da Huawei. Já foi integrado uma vez no protótipo legado `backend/server.js` (removido no commit `bf6207e`, migração para `backend/src/`), recuperado do histórico do git.

Modelo acordado: cada VM tem uma "origem" — `cloud8` | `coc` | `portal` (fallback: sem registro em Cloud8/COC, o Portal nativo do Ananim assume).

12. **Causa raiz de verdade do "chave de criptografia não encontrada": não era o backend, era o `web.config` do IIS bloqueando a URL antes do Express nem ver a requisição.**
    - `web.config` tem `requestFiltering > hiddenSegments` com `<add segment="config" />` — pensado pra bloquear acesso HTTP à pasta `config/` da instalação (onde ficam `hana-clients`, `sql-clients` etc.). O IIS casa por **segmento exato da URL** (cada parte entre `/`), não pelo path inteiro — e `/api/cloud8/config` tem "config" como terceiro segmento, batendo na regra.
    - **Como cheguei lá**: decriptei `logs/requests.log` de produção (mesmo esquema AES-GCM dos outros logs, reusando `getLogCryptoKey()`/`decryptLine()` num script descartável) filtrando por "cloud8" — só apareceram 3 chamadas de `GET /api/cloud8/reconciliation` (400, credenciais não configuradas — o próprio João testando a tela `/automacoes` sem saber que precisava configurar antes). **Nenhuma entrada pra `/api/cloud8/config`, nem GET nem PATCH** — apesar do `requests.log` registrar TUDO, inclusive os 400. Se o pedido nunca chega no middleware de log do Express, ele nunca chegou no Express — só podia ser bloqueio antes disso (IIS). Revisei `web.config` e achei o `hiddenSegments` na hora.
    - Isso também explica a mensagem genérica "Erro na requisição" que o usuário via: a página de erro do IIS (404.8, HTML) não é o JSON `{error: "..."}` que nosso `catch` monta — o `res.json().catch(() => ({}))` do `client.ts` engole o erro de parse, vira `{}`, e cai no fallback genérico.
    - **Fix**: renomeei a rota pra `/api/cloud8/credentials` (`routes/cloud8.js` + `client.ts`) — não afrouxei o `hiddenSegments` (ele protege a pasta `config/` de verdade, isso é legítimo). Grep confirmou: nenhuma outra rota do projeto tem "config" como segmento exato (rotas tipo `billing-config` são um segmento SÓ, "billing-config", não batem no filtro).
    - **Lição pra próxima sessão**: quando uma rota nova em `/api/*` "não funciona" sem erro nenhum que faça sentido, checar primeiro se o nome de algum segmento colide com `hiddenSegments` do `web.config` — sintoma é sempre o mesmo (não aparece em `requests.log`, frontend recebe resposta sem JSON de erro).
